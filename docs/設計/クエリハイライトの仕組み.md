# クエリハイライトの仕組み（Result/Query/ / Result/Tables/）

対象: `frontend/js/pages/components/Result/Query/`, `frontend/js/pages/components/Result/Tables/`

## 概要

結果画面（`/result`）では、テーブル一覧からテーブル名をクリックすると、そのテーブルが使われているSQLの該当部分が黄色く（`<mark>`）ハイライトされる。これはエラー箇所の表示ではなく、「クリックしたテーブルが元SQLのどの部分に対応するか」を可視化するナビゲーション機能。

`Result/Query/`・`Result/Tables/`はいずれも、状態を持つ「コントローラー」1ファイルと、状態を持たない「純粋関数」複数ファイルという同じパターンで構成されている。

## ファイル構成

```
Result/Query/
  QueryDisplayController.js   状態(_queryLineOffsets)を持ち、displayQuery/highlightQueryを公開する
  splitLinesWithOffsets.js    クエリ文字列を行ごとのオフセット配列に変換する（純粋関数）
  renderQuery.js              行オフセット配列とハイライト範囲を受け取り、DOMを描画する（純粋関数）
  buildLineContentHtml.js     1行分の表示HTML(ハイライト込み)を組み立てる（純粋関数）
  escapeHtml.js               HTMLエスケープ（純粋関数）

Result/Tables/
  TableListController.js      状態を持たず、テーブル一覧欄(.tables-list)全体を描画するエントリーポイント
  createDepthGroup.js         depthごとのグループ要素を作る（純粋関数）
  createQueryBlockGroup.js    1クエリブロック分のテーブル項目群をまとめた要素を作る（純粋関数）
  createTableItem.js          テーブル名ボタン1つを作り、クリックでhighlightQueryを呼ぶ（純粋関数）
```

状態(`_queryLineOffsets`)を持つのは`QueryDisplayController.js`だけで、他のファイルはすべて引数だけで完結する純粋関数になっている。`Tables/`側はそもそも状態を持たず、`displayTables(queryBlocks)`が呼ばれるたびに引数だけから完全に描画し直す。

依存関係（一方向）:
- `QueryDisplayController.js` → `splitLinesWithOffsets.js`
- `QueryDisplayController.js` → `renderQuery.js` → `buildLineContentHtml.js` → `escapeHtml.js`
- `Tables/TableListController.js` → `createDepthGroup.js` / `createQueryBlockGroup.js` → `createTableItem.js` → `Query/QueryDisplayController.js`（`highlightQuery`を呼ぶ）

## データフロー

1. バックエンドの `/run-query` がSQLを解析し、サブクエリ単位の「クエリブロック」ごとに `start_index`/`end_index`（元クエリ文字列内での開始・終了の文字オフセット）と使用テーブル一覧を返す（`backend/api/schemas/run_query.py` の `QueryBlockAnalyzeResult`）
2. `ResultPageController.js` がレスポンスを受け取り、`displayQuery(queryInfo.query)` でSQL全文を行番号つきで表示し、`displayTables(queryBlocks)` でテーブル名ボタン一覧を描画する
3. `displayQuery()` の内部で `splitLinesWithOffsets(query)` が実行され、SQLを行ごとに分割し、各行が元クエリ文字列内で何文字目から始まり何文字目で終わるか（`start_index`/`end_index`）を記録した配列を`QueryDisplayController.js`内の `_queryLineOffsets` にキャッシュしたうえで初期描画（ハイライトなし）を行う
4. `displayTables(queryBlocks)`は各クエリブロックについて`createQueryBlockGroup`→`createTableItem`でテーブル名ボタンを作る。`createTableItem`がボタンの`click`リスナーを登録し、その場で`queryBlock.start_index`/`end_index`をクロージャで捕捉する
5. ユーザーがテーブル名ボタンをクリックすると、`createTableItem`が登録した`click`リスナーが`highlightQuery(queryBlock.start_index, queryBlock.end_index)`を呼ぶ
6. `highlightQuery()` は `renderQuery(_queryLineOffsets, {start_index, end_index})` を呼び、`renderQuery`が各行について`buildLineContentHtml`を呼んで、該当箇所を `<mark>` で囲んだHTMLを組み立てる

## `buildLineContentHtml`のハイライト判定（5パターン）

`highlightRange`と行(`lineOffset`)の位置関係を、次の5パターンに明示的に場合分けして判定している。

1. **1文字も重なっていない** (`noOverlap`) → 通常表示
2. **行全体に重なっている** (`touchesLineStart && touchesLineEnd`) → 行全体を`<mark>`
3. **前半（先頭〜途中）だけ重なっている** (`touchesLineStart && !touchesLineEnd`) → 先頭から`<mark>`、末尾は通常
4. **後半（途中〜末尾）だけ重なっている** (`!touchesLineStart && touchesLineEnd`) → 先頭は通常、末尾まで`<mark>`
5. **真ん中（途中〜途中）だけ重なっている** (`!touchesLineStart && !touchesLineEnd`) → 前後とも通常、中央だけ`<mark>`

`touchesLineStart`/`touchesLineEnd`という2つの真偽値の組み合わせのうち「両方true」はパターン2で先に処理されるため、残り3通り（3・4・5）は自動的に排他的になり、抜け漏れなく網羅できる。

### 具体例

入力SQL:
```sql
SELECT * FROM (
SELECT id, name FROM users
) AS u
```

```js
_queryLineOffsets = [
  { text: "SELECT * FROM (",            start_index: 0,  end_index: 15 },
  { text: "SELECT id, name FROM users", start_index: 16, end_index: 42 },
  { text: ") AS u",                     start_index: 43, end_index: 49 },
]
```

`highlightQuery(16, 42)`（"users"ボタンをクリック）の場合:

| 行 | 判定 | 結果 |
|---|---|---|
| `SELECT * FROM (` (0-15) | `noOverlap`（`42<=0`は偽だが`16>=15`が真） | 通常表示 |
| `SELECT id, name FROM users` (16-42) | `touchesLineStart && touchesLineEnd`（`16<=16`かつ`42>=42`） | 行全体を`<mark>` |
| `) AS u` (43-49) | `noOverlap`（`42<=43`が真） | 通常表示 |

`highlightQuery(27, 31)`（"name"だけをハイライトしたい場合）なら、2行目は`touchesLineStart`(`27<=16`は偽)も`touchesLineEnd`(`31>=42`は偽)も満たさないため**パターン5（真ん中）**に該当し、`"SELECT id, <mark>name</mark> FROM users"`のように中央だけがハイライトされる。

## 既知の制約・今後の検討事項

- `highlightQuery`は`displayQuery`が先に呼ばれている前提の暗黙の呼び出し順序に依存している。現状の実際の呼び出し順序（`ResultPageController.js`で`displayQuery`→`displayTables`→クリックで`highlightQuery`）では問題にならないが、構造的に強制されているわけではない点に注意
- このプロジェクトはバンドラーを使わずネイティブESモジュールで配信しているため、`Result/Query/`・`Result/Tables/`フォルダをimportする際は`index.js`のような自動解決はできず、常にファイル名まで明示する必要がある
- `renderQuery`はハイライトの有無に関わらず`.query-display`の全行を毎回作り直す設計。差分更新（ハイライト対象の行だけ書き換える）はしていない。数百行程度のクエリでは体感できる性能劣化はないと考えられるが、実測はしていない
