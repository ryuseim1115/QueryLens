# 学んだこと・課題と対策（オリジナルプロダクト: QueryLens）

実際の開発履歴（コミット・障害対応）をもとに、事実 / 考察 / 解決 / 再発防止 の形式でまとめる。

---

## 1. デプロイ後、uvicornがSSHセッション終了と共に落ちる

**事実：** オリジナルプロダクトのデプロイで、SSH経由で `uvicorn` を起動していたが、デプロイスクリプトのSSHセッションが終了すると同時にプロセスも終了し、アプリが応答しなくなった（2026-06-21）。

**考察：** シェルから直接起動したプロセスは、親であるSSHセッションが切れるとSIGHUPを受けて終了する。デプロイの「起動コマンドを実行できた」ことと「起動し続けていること」を混同していた。

**解決：** まずバックグラウンド起動（`&`）に変更したが不十分だったため、`setsid` でセッションから完全に切り離し起動ログも出力するようにした。最終的には `systemd` サービスとして管理する方式に切り替え、恒久対応とした。

**再発防止：** 常駐プロセスは最初から `systemd`（や同等のプロセスマネージャ）管理を前提に設計する。デプロイ後にプロセスが生存しているかをヘルスチェックで確認する工程を入れる。

## 2. SSHタイムアウトでデプロイが途中失敗する

**事実：** `poetry install` に時間がかかり、デプロイワークフローのSSHタイムアウトに達して失敗した（2026-06-21）。

**考察：** 依存パッケージが増えるほどインストール時間は伸びるため、固定の短いタイムアウトは将来的に必ず問題になる。

**解決：** SSHのタイムアウトを30分に延長した。

**再発防止：** 時間のかかる処理を含むCI/CDのタイムアウトは余裕を持って設定し、依存が増える見込みがあるステップは特に注意する。

---

## 3. poetry installが一時的に失敗することがある

**事実：** `poetry install` がネットワーク等の理由で一時的に失敗し、デプロイが失敗することがあった（2026-06-21）。

**考察：** 外部レジストリへのアクセスを伴うコマンドは、一過性のエラーが避けられない。

**解決：** `poetry install` にリトライ処理を追加した。

**再発防止：** 外部通信を伴うCI/CDのステップには、最初からリトライを組み込んでおく。

---

## 4. push と pull_request の両方でCIが二重実行される

**事実：** CIのトリガーが `push` と `pull_request` の両方に設定されており、同じ変更に対してCIが二重に走っていた（2026-06-21）。

**考察：** ブランチへのpushとPRの両方をトリガーにすると、同一コミットに対して重複実行が起きやすい。当初トリガー設計を精査していなかった。

**解決：** `push` トリガーを削除し `pull_request` のみに統一した。

**再発防止：** CIのトリガー設計は、「何をもって1回の検証とみなすか」を最初に決めてから設定する。

---

## 5. python-multipartが依存関係から漏れておりアップロード機能が動かない

**事実：** FastAPIのフォーム/ファイルアップロード（CSVアップロード機能）に必要な `python-multipart` が `pyproject.toml`/`poetry.lock` に含まれておらず、実行時エラーになった（2026-06-21）。

**考察：** ローカル環境にたまたま入っていた、あるいは該当コードパスをローカルで十分にテストしていなかったため、依存漏れがCIやローカル実行では顕在化しなかった。

**解決：** `python-multipart` を依存関係に追加した。

**再発防止：** 新しい外部ライブラリ機能（ここではFastAPIのファイルアップロード）を使う際は、クリーンな環境（`poetry install` からやり直した状態）で動作確認する。

---

## 6. 大容量CSV（合計450万行超）をgit管理してしまいリポジトリが肥大化

**事実：** 動作確認用の大容量CSV（`tmp/orders.csv` など、5ファイル合計450万行超）が `.gitignore` されておらずコミットされていた。後から `.gitignore` に追加し、トラッキングを解除した（2026-06-21）。

**考察：** 一時的な検証用データを `tmp/` のような「一時ディレクトリ」に置くだけでは、`.gitignore` に明示しない限りgit管理から漏れない。ディレクトリ名による「一時である」という意図は、gitには伝わらない。

**解決：** `.gitignore` に `tmp/` を追加し、既にコミットされていたファイルを履歴から除外した。

**再発防止：** 検証用の一時ファイル・大容量データを置くディレクトリは、使い始める前に `.gitignore` に登録する。`git status` で意図しない大きなファイルが追跡対象になっていないか、コミット前に確認する習慣をつける。

## 7. ローカルCSV解析からS3接続への設計変更

**事実：** 当初はローカルファイルシステム上のCSVを解析対象とする設計だったが、後に「ローカルCSVを解析対象としていたのをS3に変更」する形で設計を変更した。

**考察：** ローカルパス前提の設計は、開発環境では動くが、デプロイ先（本番サーバー）でのファイル配置・永続化の方法まで考慮できていなかった。データソースの置き場所は早い段階でインフラ構成と合わせて決めるべきだった。

**解決：** データソースをS3に統一し、以降の実装・設計方針（メモリにも記録済み）としてローカルCSV方式は採用しないことを明確にした。

**再発防止：** データの永続化・参照方式を決める際は、ローカル開発環境だけでなく本番のインフラ構成（ファイルシステムの永続性、複数インスタンス間の共有可否）を前提に検討する。

---

## 8. リファクタ後にテストが旧構成を参照したままCIが失敗

**事実：** バックエンドの層を `infrastructure` 配下に再編するリファクタを行った際、`tests/conftest.py` が旧 `api.db.connection` を参照したままになっており、CIが失敗した（2026-07-04）。あわせてruffのimport順違反、未使用変数も検出された。

**考察：** プロダクションコードのリネーム・移動は追跡できても、テスト側の参照更新を漏らしやすい。IDEの一括リネームや `grep` での参照確認を徹底していなかった。

**解決：** `conftest.py` の参照を修正し、import順・未使用変数も合わせて修正した。

**再発防止：** ファイル移動・リネームを伴うリファクタでは、`grep -rn` などで旧パス・旧シンボル名の参照が残っていないか機械的に確認してからコミットする（このセッションでの `table_extractor.py` → `table_name_extractor.py` のリネームでも同様に全参照を検索して確認した）。

## 9. 本番にMySQLが未構築のままログイン機能をデプロイしアプリがクラッシュ

**事実：** register/login機能（MySQL連携）を含むPRを初めて`production`にデプロイした際、本番にMySQLサーバーが存在せず、`MYSQL_URL`等もSecrets未登録だったため、モジュール読み込み時の `create_engine(MYSQL_URL)` が失敗しアプリごと起動クラッシュした。`/login` が404を返す状態になった。

**考察：** デプロイワークフローがSSHスクリプトの終了コードしか見ておらず、デプロイ後にアプリが実際に正常応答するかまで検証していなかった（ヘルスチェック不在）。また、本番MySQL未構築は既知のIssue（#79）として記録されていたにもかかわらず、それをブロッカーとして扱わずマージしてしまった。

**解決：** 応急対応として、専用EC2の新規構築を待たず同一インスタンスにMySQLをローカルインストールし、Secrets追加と `deploy.yaml` の修正で暫定稼働させた。

**再発防止：** デプロイワークフローに疎通確認（ヘルスチェック）を追加する。新機能が新しい環境変数・外部インフラ依存を追加する場合、マージ前に本番側の準備状況を確認する。既知のブロッカーIssueがある機能はそれが解決するまで本番マージを控える。

## 10. 責務が混在したモジュールと、コメント・テスト不足で仕様が読み取りにくい

**事実：** `query_structure` 配下のクエリ解析処理で、SQL文字列をASTにパースする関数（`parse_query_block`）が「テーブル抽出」を責務とするファイルに同居していた。また `VALUES` 句など「テーブルでもサブクエリでもないFROM対象」を無視するガード処理（`any(table_name_alias)`）にテストがなく、コメントもなかった。

**考察：** 小さなヘルパー関数を「とりあえず動く場所」に置いたまま放置すると、ファイル名と実際の責務がずれ、後から読む際に迷う。エッジケースの分岐は、対応するテストとコメントがないと「意図した挙動」なのか「未考慮のバグ」なのか判別できない。

**解決：** パース処理を `query_parser.py` に分離し、テーブル抽出関数・ファイル名を実態（テーブル名とエイリアスを抽出する）に合わせてリネームした。`VALUES` 句のような非テーブル・非サブクエリのケースにテストとコメントを追加し、仕様を `docs/設計/テーブル名抽出仕様.md` にまとめ、レビュー用にIssue #98を起票した。

**再発防止：** ヘルパー関数を追加する際は、置き場所となるファイルの責務と一致するかを都度確認する。分岐が生まれるエッジケースには、実装と同時にテストとコメント（なぜその分岐が必要か）を追加する。

## 11. 見慣れない構文をPython2の古い構文と誤認し、正しいコードを壊しかけた

**事実：** `backend/api/routers/upload_csv.py` の `except UnicodeDecodeError, csv.Error:` という記法を、Python2の無効な構文（`SyntaxError`の原因）と判断し `except (UnicodeDecodeError, csv.Error):` に「修正」したところ、CIの `ruff format --check` が失敗した。調査の結果、`pyproject.toml` の `requires-python = ">=3.14"` によりruffのターゲットがPython 3.14になっており、PEP 758（括弧なしの複数例外型）が正規スタイルとして採用されていたため、修正前の括弧なし形式がもともと正しいコードだった（2026-07-06, PR #85）。

**考察：** 見慣れない構文＝古い/誤った構文と早合点し、プロジェクトが実際に何のPythonバージョンをターゲットにしているか（`pyproject.toml` の `requires-python`）を確認しないまま「修正」してしまった。CIが落ちたことで誤りに気づけたが、CIがなければ動作するコードを壊していた可能性がある。

**解決：** 括弧なしの元の形式に戻し、`ruff check`・`ruff format --check` の両方が通ることを確認した。

**再発防止：** 見慣れない構文に遭遇したら、まず対象言語のバージョンやターゲット設定（`pyproject.toml` の `requires-python` など）を確認し、そのバージョンで正当な構文かどうかを調べてから「間違い」と判断する。特に新しい言語バージョンの構文（PEPなど）は、慣れている古い知識だけで判断しない。

## 12. セッションCookieの有効期限がデフォルト値のまま14日間になっていた

**事実：** `backend/main.py:24` の `SessionMiddleware` に `max_age` を明示的に指定しておらず、Starletteのデフォルト値である `1209600`秒（14日間）がセッションCookieの有効期限として使われていた。ログアウト機能（Issue #80）も未実装のため、ユーザー自身がセッションを終了する手段もない状態だった（Issue #95, 2026-07-09時点でOPEN・priority: high）。

**考察：** 認証まわりのミドルウェアを導入した際、ライブラリのデフォルト値をそのまま使うとセキュリティ要件を満たさない場合があることを見落としていた。共有PCなど不特定多数がアクセスしうる端末では影響が大きい。

**解決：** Issue #95として起票済み。対応方針（`max_age` を数時間〜1日程度に短縮、`https_only`/`same_site` 等のCookie属性の見直し）は案として整理済みだが、本記録時点では未対応。

**再発防止：** 認証・セッション関連のミドルウェアを導入する際は、デフォルト値をそのまま使わず、有効期限やCookie属性をセキュリティ要件と照らして明示的に設定する。あわせてログアウト機能のような「利用者自身がセッションを終了する手段」も認証機能と同時に検討する。

## 13. CSVアップロード後の一覧更新処理が、複数ファイル同時アップロード時に競合する設計だった

**事実：** `frontend/js/pages/components/input/FileDialog/UploadFile.js` では、アップロード成功後に毎回 `reloadFileList()` を呼んでいた。この関数は「ストレージとインメモリの差分を取得し、一覧をいったん空にしてから作り直す」処理（`clearFileList()` → 既存分の表示 → 未インポート分を1件ずつテーブル作成しながら追加）を行う。加えて、アップロード完了処理では `selectFileBtn` を `reloadFileList()` の完了を待たずに再度有効化していたため、1件目の `reloadFileList()` が完了する前にユーザーが2件目のファイルをアップロードでき、`reloadFileList()` が2重に走る状態が発生し得た。2つの `reloadFileList()` は互いに別々のタイミングで取得したスナップショットに基づいて動作するため、一方の `clearFileList()` がもう一方が追加している最中の一覧表示を消してしまう競合が起きる設計だった。

**考察：** 「全件の差分を取得し、一覧を消してから作り直す」という処理は、1回だけ・排他的に実行される前提でしか安全に動かない。ユーザー操作（連続アップロード）によって同じ処理が非同期に複数回呼ばれうることを考慮していなかった。UI操作を無効化するタイミング（ボタンのdisabled解除）と、実際に処理が完了するタイミングがずれていたことも一因。

**解決：** 対応方針として、①そのファイル1件だけ「テーブル作成→一覧に1行追加」する `createTableAndAppendRow(fileName)` を切り出し並列実行を安全にする案と、②`reloadFileList()` の完了を待つまでアップロード操作自体をできなくして直列化する案を検討した。実装をシンプルに保つことを優先し、最終的に②を採用した。`UploadFile.js` の `selectFileBtn.disabled = false`（次のファイル選択を許可する処理）を `await reloadFileList()` の**後**に移すことで、1件目の `reloadFileList()` が完了するまで2件目のアップロード操作自体を受け付けないようにした。これにより `reloadFileList()` が同時に2つ走ることがなくなり、`createTableAndAppendRow` のような専用の並列安全設計は不要になった。

**再発防止：** 複数の非同期処理（連続したユーザー操作など）から同時に呼ばれうる関数を設計する際は、「その時点のスナップショット全体を取得し、消してから作り直す」処理を安易に採用しない。安全にするアプローチは大きく2通りある。(a) 各呼び出しが「自分の担当分だけ」を扱い他の状態を破棄・上書きしない加算的（additive）な設計にして並列実行自体を許容する、(b) UIの有効/無効化を対応する非同期処理の完了タイミングと厳密に一致させ、そもそも同時実行させない（直列化する）。前者は並列性を活かせるが設計が複雑になり、後者はシンプルだが並列の恩恵はない。要件と実装コストを踏まえてどちらを取るか判断する。
